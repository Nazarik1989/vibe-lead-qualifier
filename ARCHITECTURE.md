# Архитектура Vibe Lead Qualifier

Документ описывает границы и решения демонстрационного MVP. Контракт интеграции сверен 28.07.2026 с [официальной документацией VibeMarketolog Agent API](https://lk.vibemarketolog.ru/docs/agent-api) и [официальным OpenAPI 3.1](https://lk.vibemarketolog.ru/api/agent/openapi.json).

## Цели

- безопасно принять подписанное событие VibeMarketolog;
- накопить бриф одного лида из нескольких сообщений;
- дать полезный синхронный ответ за ограниченное время webhook;
- сформировать и сохранить ответ с одним разрешённым CRM-действием при готовности брифа;
- воспроизводимо работать и тестироваться без LLM, Bitrix credentials и платных вызовов;
- оставить явную точку расширения для более сильного extractor.

Не цели MVP: непосредственное выполнение Bitrix REST, универсальный NLU, distributed deployment, долговременное защищённое PII-хранилище и автоматическая генерация контента.

## Контекст

```text
Внешний канал
    │
    ▼
VibeMarketolog ── signed POST ──► /webhooks/vibe
                                      │
Локальный оператор ── unsigned ──► /demo/messages (только при ENABLE_DEMO_ENDPOINTS=true)
                                      │
                                      ▼
                              QualificationService
                               │              │
                               ▼              ▼
                           Extractor       Repository
                                            SQLite
                                      │
                                      ▼
                              reply + actions[]
                                      │
                                      ▼
                          Vibe / Bitrix24 bridge
```

Исходящие обращения к Vibe API вынесены в отдельный async-клиент и используются CLI. Основной локальный сценарий от них не зависит.

## Слои и ответственность

### HTTP-слой

FastAPI всегда регистрирует два маршрута:

- `GET /health` — минимальный liveness/status;
- `POST /webhooks/vibe` — доверенная граница для подписанных событий;

При `ENABLE_DEMO_ENDPOINTS=true` дополнительно регистрируются:

- `POST /demo/messages` — адаптер локального сообщения без подписи;
- `GET /demo/dialogs/{dialog_id}` — чтение состояния demo-диалога.

HTTP-слой читает raw body один раз, передаёт его verifier до разбора JSON, преобразует ожидаемые ошибки в HTTP-ответы и не содержит бизнес-правил квалификации.

### Верификация и нормализация webhook

Verifier новой схемы вычисляет hex HMAC-SHA256 от точных байтов HTTP body с `VIBE_WEBHOOK_SECRET` и сравнивает результат с `X-Vibe-Signature` через `hmac.compare_digest`.

Документация описывает legacy-секрет как SHA-256 от raw API token для старых ключей. Проект сознательно его не поддерживает: API token не должен становиться частью входящего verifier. Оператору старого ключа нужно выпустить ключ с отдельным `webhook_secret`.

Нормализатор отделён от квалификации. Для `agent.message` он принимает документированные поля сообщения:

- плоско в теле события;
- либо под ключом `message`.

Причина — актуальная документация показывает поля сообщения и сообщает, что они попадают в webhook-payload, но не приводит точную JSON-оболочку push webhook. Поддержка двух форм — локальное решение совместимости, а не новая спецификация Vibe.

### QualificationService

Application service организует один use case:

1. определить идентификаторы диалога и сообщения;
2. найти ранее сохранённый результат;
3. загрузить состояние диалога;
4. извлечь кандидаты полей из нового текста;
5. слить только полезные значения с накопленным брифом;
6. выбрать следующий конкретный вопрос либо сформировать итог;
7. сохранить состояние и результат идемпотентности;
8. вернуть тот же результат при повторной доставке.

Сервис не знает HTTP-заголовков и не вызывает Bitrix24. CRM-команда — типизированная часть ответа, исполняемая внешним мостом.

### Extractor

MVP использует правила и регулярные выражения:

- предсказуемая стоимость — ноль внешних запросов;
- низкая задержка;
- объяснимость каждого распознанного поля;
- стабильные unit-тесты.

Extractor скрыт за интерфейсом. Будущая LLM-реализация должна вернуть тот же доменный результат и не получать доступ к репозиторию, webhook secret или выполнению actions.

### Repository

SQLite хранит две логические сущности:

- состояние диалога: собранные поля брифа и служебные отметки;
- обработанное сообщение/событие: идемпотентный ключ и сериализованный ответ.

Стабильный message ID — предпочтительный ключ. Если платформа его не передала, используется воспроизводимый fingerprint доступных полей события. Это защищает от обычного retry, но не заменяет официальный delivery ID.

Граница записи должна сохранять обновлённый бриф и результат обработки согласованно. Уникальность идемпотентного ключа является последней защитой от конкурентного дубля в рамках одной SQLite-базы.

### Vibe API client и CLI

Типизированный async-клиент инкапсулирует Bearer auth, настраиваемый через `HTTP_TIMEOUT_SECONDS` таймаут, JSON и ошибки для:

- `GET /api/agent/me`;
- `POST /api/agent/webhook-test`;
- `POST /api/agent/webhook-url`;
- `POST /api/agent/generate/estimate`;
- `GET /api/agent/inbox`;
- `POST /api/agent/inbox/{id}/reply`.

OpenAPI указывает scope `read` для чтения inbox и `write` для регистрации webhook URL и отправки reply. Там, где успешная response schema пока не задана, модели разрешают дополнительные поля и не выдумывают обязательный формат ответа.

CLI — тонкий операторский адаптер. В нём нет команды `POST /generate`: оценка остаётся бесплатным dry-run, а реальная платная операция не может запуститься случайно.

## Последовательности

### `agent.message`

```text
Vibe            API          Verifier       Service       SQLite
 │ signed POST   │              │              │             │
 ├──────────────►│ raw bytes    │              │             │
 │               ├─────────────►│              │             │
 │               │ valid        │              │             │
 │               │◄─────────────┤              │             │
 │               │ normalize + process         │             │
 │               ├────────────────────────────►│ lookup      │
 │               │                             ├────────────►│
 │               │                             │ state/result│
 │               │                             │◄────────────┤
 │               │                             │ extract     │
 │               │                             │ persist     │
 │               │                             ├────────────►│
 │               │ reply + optional action     │             │
 │               │◄────────────────────────────┤             │
 │ HTTP 2xx JSON │              │              │             │
 │◄──────────────┤              │              │             │
```

Повтор с тем же идемпотентным ключом заканчивается после lookup, не меняет локальное состояние и возвращает сохранённый ответ целиком. Поскольку ответ содержит тот же action, SQLite предотвращает повторную локальную обработку, но не гарантирует отсутствие повторного вызова Bitrix24 внешним мостом.

### Служебные события

- `webhook.test` подтверждается успешным ответом и позволяет официальному self-test проверить listener и HMAC;
- `generation.complete` и `generation.error` принимаются и подтверждаются, но не участвуют в квалификации лида;
- неизвестный `event` безопасно подтверждается без изменения состояния диалога.

Такой диспетчер не падает при расширении списка событий на стороне платформы.

## Формирование брифа и action

Поля брифа:

| Поле | Назначение |
| --- | --- |
| `name` | имя лида |
| `service` | услуга или задача |
| `budget` | нормализованный бюджет |
| `deadline` | срок в исходной понятной формулировке |
| `contact` | телефон, email или иной контакт |
| `comment` | дополнительный контекст |

Обязательны `name`, `service`, `budget`, `deadline` и `contact`; `comment` остаётся опциональным. Если обязательного поля нет, сервис задаёт только один вопрос, чтобы диалог не выглядел как анкета. Когда обязательный набор заполнен, builder создаёт только `crm.deal.add` с контролируемыми полями. Текст пользователя не может подменить имя метода action.

## Идемпотентность и replay

Есть три разных свойства:

1. **Local processing idempotency** — реализована сохранением состояния и ответа по message ID/fingerprint. Повтор не запускает extractor и builder повторно.
2. **External side-effect idempotency** — не гарантирована. Сохранённый ответ намеренно включает исходный action: удалять его при retry небезопасно, потому что первый HTTP-ответ мог потеряться. Exactly-once выполнение требует стабильного `action_id`/idempotency key, дедупликации на стороне моста и доступного результата исполнения.
3. **Криптографическая anti-replay защита по времени** — полностью не реализуема из текущего документированного контракта: для всех webhook не указан универсальный delivery ID и подписанный delivery timestamp.

HMAC доказывает целостность и знание секрета, но сам по себе не доказывает свежесть сообщения. Поэтому fingerprint — честный MVP-компромисс для локальной обработки. Предпочтительное развитие: официальный `X-Vibe-Delivery-Id`, `X-Vibe-Timestamp` и подпись timestamp вместе с raw body.

## Ошибки и отказоустойчивость

- отсутствующая или неверная подпись отклоняется до JSON-парсинга;
- невалидный JSON не попадает в бизнес-логику;
- неизвестное событие не ломает endpoint;
- timeout, transport error, 4xx и 5xx Vibe API преобразуются клиентом в контролируемые ошибки;
- секреты и полное тело с PII не должны попадать в журнал;
- webhook-обработка синхронная и не содержит медленных внешних вызовов.

Официальная документация сообщает для generation callbacks три retry с задержками 30/120/600 секунд и считает любой 2xx успешной доставкой. Для `agent.message` требуется синхронный ответ не позднее 18 секунд; детерминированный локальный путь оставляет большой запас.

## Модель угроз

| Риск | Контроль MVP | Остаточный риск |
| --- | --- | --- |
| Подделка webhook | HMAC raw body + constant-time compare | компрометация secret |
| Повторная доставка | message ID/fingerprint + сохранённый ответ для локальной обработки | нет временного anti-replay; мост может повторно исполнить action |
| Инъекция CRM-команды | точный allowlist `crm.deal.add` | значения полей требуют бизнес-валидации |
| Утечка credentials | env, редактирование логов, отсутствие token-derived legacy | защита среды вне приложения |
| Утечка PII | минимизация логирования | SQLite не шифруется приложением |
| SSRF через callback | проект не загружает URL из webhook | туннель и внешняя платформа вне границы |
| Случайное списание | нет команды generate; estimate-only | ручные запросы вне проекта |

## Почему это не production-ready

- SQLite и локальный файл не дают HA и межузловую координацию;
- нет миграционного контура, backup/restore и retention policy;
- включённый demo API не имеет auth и rate limiting;
- нет шифрования PII at rest и tenant isolation;
- нет receipt/status или очереди/outbox для отслеживания результата CRM action;
- эвристический extractor покрывает только ограниченные формулировки;
- нет OpenTelemetry, SLO, алертов и нагрузочных тестов;
- отсутствует полноценная freshness-проверка webhook;
- официальный OpenAPI опубликован, но Bridge/Webhook request/response-схемы в нём неполны, поэтому полноценные contract-тесты для этих payload пока невозможны.

## Путь к production

1. PostgreSQL, миграции и транзакционный outbox.
2. Delivery ID/timestamp, nonce cache и ограниченное окно replay.
3. Сохранять demo-маршруты выключенными публично; добавить авторизацию, если их потребуется разрешить вне локальной среды.
4. Vault/KMS, шифрование чувствительных полей, TTL и запрос на удаление данных.
5. Наблюдаемость и redaction-политика, rate limiting, bounded request size.
6. Schema-guided LLM extractor с confidence, human confirmation и deterministic fallback.
7. Стабильный `action_id`/idempotency key, дедупликация мостом, receipt/status результата CRM action и аудит фактического создания сделки.
