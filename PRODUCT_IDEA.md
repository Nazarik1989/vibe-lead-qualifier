# Продуктовая идея

## Ценность

Vibe Lead Qualifier превращает свободный чат в управляемый процесс квалификации: клиент отвечает естественным языком, агент помнит уже сообщённое, спрашивает только недостающее и передаёт в CRM структурированную сделку. Для бизнеса это означает меньше ручного копирования, меньше потерянных лидов и дублей; для клиента — короткий диалог вместо длинной формы.

MVP также демонстрирует полезный принцип для Agent API: AI-сценарий должен быть безопасным интеграционным компонентом, а не только генератором текста. Здесь это выражено в проверке webhook, локальной идемпотентности обработки, явном allowlist CRM-action и отсутствии скрытых платных операций.

## Граница проверки

Предложения ниже сверены 28.07.2026 с [официальной страницей Agent API](https://lk.vibemarketolog.ru/docs/agent-api), на которой указано обновление от 27.07.2026, с live-каталогом `/capabilities` и с [официальным OpenAPI 3.1](https://lk.vibemarketolog.ru/api/agent/openapi.json). Формулировка «не документировано» означает наблюдаемый пробел этих публичных контрактов, а не доказательство отсутствия внутренней реализации.

## 1. Универсальный delivery ID и подписанный timestamp

**Что уже есть.** Для callback генерации документированы `X-Vibe-Generation`, `generation_id`, `attempt`, а тело защищено `X-Vibe-Signature`. В сообщениях канала встречаются `message_id` и клиентский `X-Idempotency-Key`.

**Наблюдаемый пробел.** Не описаны единый уникальный идентификатор каждой webhook-доставки и подписанное время доставки, одинаковые для `agent.message`, `webhook.test`, `generation.complete` и `generation.error`. `created_at`/`completed_at` генерации описывают ресурс, а не свежесть конкретной доставки. Для `agent.message` точная оболочка push-payload вообще не показана.

**Предложение.** Добавить заголовки:

```text
X-Vibe-Delivery-Id: evt_...
X-Vibe-Timestamp: 1785254400
X-Vibe-Signature: hex(hmac_sha256("<timestamp>.<raw_body>", webhook_secret))
```

Delivery ID позволяет однозначно дедуплицировать доставку у получателя, timestamp — задать окно anti-replay, например ±5 минут. Документации стоит задать срок уникальности ID, допустимый clock skew и одинаковую семантику повторной попытки: новый attempt, но тот же delivery/event ID либо два явно разделённых ID.

## 2. Schema-guided structured output для ответов агента

**Что уже есть.** `GET /capabilities` описывает параметры моделей; `strict=true` и `/generate/estimate` проверяют вход генерации. CRM-actions документированы как массив объектов, мост применяет whitelist и фильтрует распарсенный JSON ответа модели.

**Наблюдаемый пробел.** На проверенной странице нет контракта, позволяющего агенту передать JSON Schema для результата текстовой генерации или зарегистрировать версионированную схему `reply + actions`. Фильтрация после свободного model output полезна, но не даёт вызывающей стороне гарантии формы до парсинга.

**Предложение.** Поддержать schema-guided output:

```json
{
  "response_format": {
    "type": "json_schema",
    "name": "qualified_lead_v1",
    "strict": true,
    "schema": {}
  }
}
```

API должен либо вернуть результат, валидный по схеме, либо типизированную ошибку без частично исполняемых actions. Для CRM полезны версии схем, allowlist методов/полей на уровне токена и `dry_run` валидации action до передачи мосту.

## 3. Полный машинный контракт Bridge/Webhook и генерируемые SDK

**Что уже есть.** На дополнительной проверке обнаружен официальный OpenAPI 3.1 по адресу `/api/agent/openapi.json`; идея «создать OpenAPI» уже реализована и поэтому заменена. Спецификация задаёт production server, Bearer security, пути и `x-required-scope`. Например, она уточняет `write` для `/webhook-url` и `/inbox/{id}/reply`, что не видно в текстовом разделе Inbox.

**Наблюдаемый пробел.** В текущем OpenAPI нет раздела `webhooks`, а критичные Bridge-методы описаны неполно: успешные ответы `/inbox`, `/inbox/{id}/reply`, `/webhook-url`, `/webhook-test` не имеют JSON Schema; тела reply и регистрации webhook обозначены просто как `object`; точная оболочка `agent.message` отсутствует. Поэтому сгенерированный клиент всё ещё вынужден использовать расширяемые ручные модели именно в самой важной части интеграции.

**Предложение.** Дополнить существующий OpenAPI:

- точными request/response schemas для inbox, reply и webhook URL;
- OpenAPI Webhooks-описаниями `agent.message`, `webhook.test`, `generation.complete` и `generation.error`;
- nullable/optional semantics, примерами и единым error union;
- идентификатором версии контракта и changelog/deprecation metadata.

После этого публиковать генерируемые Python/TypeScript SDK и contract-тесты против той же спецификации. Это уменьшит расхождения ручных клиентов и даст IDE типы без копирования неполных примеров из HTML-справочника.

## 4. Идемпотентное исполнение CRM-actions и receipt результата

**Что уже есть.** Агент может вернуть `actions`, а получатель webhook способен сохранить и при retry повторить тот же HTTP-ответ. Это обеспечивает надёжную повторную доставку ответа и локальную идемпотентность обработки.

**Наблюдаемый пробел.** Публичный контракт не задаёт, дедуплицирует ли мост повторно полученный action. Удалять action из сохранённого ответа небезопасно: если первый HTTP-ответ потерялся, сделка может не создаться. Повторять action без ключа тоже небезопасно: мост может создать дубль. Агент при этом не получает подтверждённый результат исполнения.

**Предложение.** Добавить каждому action стабильные `action_id` и `idempotency_key`; мост должен атомарно дедуплицировать ключ в рамках tenant и метода и при retry возвращать прежний execution result без нового вызова Bitrix24. Результат должен содержать `status`, `external_resource_id`, `executed_at` и типизированную ошибку и быть доступен через result endpoint либо события `action.completed`/`action.failed`.

Такой контракт даст практическую exactly-once семантику внешнего side effect; без поддержки моста сервис может гарантировать только local processing idempotency.

## 5. Явная выдача и ротация webhook secret

**Что уже есть.** Документация описывает отдельный `webhook_secret`,
который показывается один раз при создании нового ключа. Live
`/webhook-test` подтвердил новую формулу
`HMAC-SHA256(raw_body, webhook_secret)`.

**Наблюдение.** В конкретном сеансе создания ключа 28.07.2026 окно
показало только `SPA_ACCESS_TOKEN` и `SPA_BASE_URL`; отдельное значение
`webhook_secret` в доступной части интерфейса не отображалось. Поэтому
пользователь может получить рабочий токен для `/me` и `/generate/estimate`,
но не иметь данных для проверки входящей подписи. Это наблюдение требует
подтверждения со стороны платформы и не обобщается на все аккаунты.

**Предложение.** Сделать выдачу секрета отдельным явным шагом:

- после создания показывать два подписанных поля с отдельными кнопками
  копирования и подтверждением «оба значения сохранены»;
- добавить безопасную ротацию только webhook secret без замены
  API-токена;
- показывать состояние `webhook secret configured`, но никогда не
  возвращать сохранённое значение;
- дать бесплатный setup-check, который проверяет URL и тестовую подпись и
  объясняет точную причину ошибки;
- синхронизировать названия переменных в UI, quick start и Agent API
  документации.

Такой onboarding уменьшит число интеграций, которые успешно проходят
Bearer-аутентификацию, но останавливаются на первом подписанном webhook.
