## Подписанный webhook

На постоянном `/webhooks/vibe` проверены четыре сценария:

- корректная HMAC-подпись — HTTP `200`;
- повторная доставка того же подписанного payload — HTTP `200`;
- неверная подпись — HTTP `401`;
- отсутствующая подпись — HTTP `401`.

Официальный бесплатный `POST /api/agent/webhook-test` был доставлен на
постоянный endpoint, получил HTTP `200` и имел стоимость `0`. Его синтетическое
событие явно сообщало, что генерация не выполнялась.

Успешный self-test подтверждает доставку одного официального
`webhook.test`. Сам по себе он не доказывает регистрацию постоянной push-
подписки `agent.message` и не подтверждает исполнение CRM-action в Bitrix24.

## Demo-сценарий и локальная идемпотентность

Трёхшаговый сценарий через защищённый `/demo/messages` вернул HTTP
`200/200/200`. Итоговая проверка состояния показала 7/7 заполненных полей и
ровно один сформированный `crm.deal.add`.

Повторная доставка последнего сообщения вернула сохранённый ответ вместе с тем
же action. При этом число строк `processed_events` осталось `3 → 3`, а
локальное состояние диалога не изменилось. Новое сообщение с новым ID после
завершения диалога не сформировало дополнительных CRM-actions.

Это подтверждает **local-processing idempotency** внутри приложения. Сервис не
получает receipt или внешний ID сделки и не контролирует дедупликацию на
стороне Vibe/Bitrix-моста, поэтому exactly-once внешний side effect не
заявляется.

## Разделение credentials

- на VPS настроен webhook secret, но отсутствует API token;
- Bearer-токен остаётся на доверенной локальной машине и нужен только исходящим
  CLI-командам;
- Basic Auth credentials и `.htpasswd` не входят в репозиторий;
- `.env`, сертификаты, private keys, SQLite и логи не входят в Git или ZIP;
- платный `POST /generate` не вызывался;
- реальные CRM-действия не исполнялись.

Quick Tunnel остановлен после внешней проверки постоянного адреса; остановленный
контейнер сохранён только как резервный rollback-вариант и не участвует в
рабочем маршруте.

Credential scan точного дерева публикации и ZIP выполняется отдельно перед
push; итоговые hash и commit SHA приводятся в отчёте о релизе v3.
